# Core Engineer: скилл для работы с ядром umbot

## Назначение

Применять, когда требуется изменить `src/core/` — главный Bot.ts, AppContext, registry команд, типы интерфейсов. Отдельно от обычного code-audit, потому что правки в ядре **опасны для публичного API** и требуют особой осторожности.

## Триггер

- "правим Bot.ts"
- "изменяю AppContext"
- "рефакторинг ядра"
- "новый метод в Bot"

## Когда НЕ использовать

- Добавление нового middleware → используй `umbot-add-middleware`
- Новая платформа → используй `umbot-platform-add`
- Фикс бага в платформе/адаптере → `umbot-platform-code-update`
- Просто багфикс по известному репорту → `umbot-fix-bug`

## Воркфлоу (строго по шагам)

### Шаг 0: Прочитай архитектурные инварианты

Перед любым изменением в `src/core/` убедись:

1. **Dependency direction**: `core` НЕ импортирует из `plugins/`. Также сам код ничего не должен знать об определенной платформе и специфике ее работы.
2. **Public API stability**: изменения должны быть обратно совместимы (или согласованы как major).
3. **Encapsulation**: внутреннее состояние ТОЛЬКО через `#field` (private fields).

### Шаг 1: Анализ — что меняешь?

| Изменение                                  | Риск        | Verify                                                       |
| ------------------------------------------ | ----------- | ------------------------------------------------------------ |
| Новый метод в `Bot`                        | Низкий      | добавь JSDoc, тест, упоминание в `src/docs/api-reference.md` |
| Изменение сигнатуры                        | **Высокий** | убедись в BC, иначе `major`                                  |
| Изменение внутренней логики (не публичное) | Средний     | все тесты должны пройти                                      |
| Изменение default поведения                | **Высокий** | нужен CHANGELOG entry                                        |
| Добавление generic параметра               | Средний     | default value для полной BC                                  |

### Шаг 2: Формулируй план

Планы в core должны отвечать:

- Какие файлы затронуты (`src/core/Bot.ts`, `src/core/utils/CommandReg.ts`, `src/controller/BotController.ts`)
- Какие интерфейсы меняются в `src/core/interfaces/`
- Backward compat: да/нет, и причина
- Где добавить тесты

### Шаг 3: Реализация

Правила:

- `#field` для внутреннего состояния
- `protected` для методов, которые могут быть переопределены в наследниках
- `private` для helpers
- `public` только для API
- Все async функции обработай `try/catch` или `.catch()` — lint не пропустит floating promises
- Все параметры типизируй, no `any`

### Шаг 4: Тесты

**Обязательно:**

1. Юнит-тест на новый метод/ветвление
2. Интеграционный тест через `BotTest`, если меняется поведение runtime-цикла
3. Регрессионный тест если чинил баг

Тесты лежат в `tests/Core/` или `tests/Bot/`, повторяют структуру src/.

### Шаг 5: Документация (часть задачи, не «потом»)

Задача не закрыта, пока документация не описывает новое поведение (AGENTS.md раздел 6).

Если добавляешь публичный метод или опцию:

- JSDoc на русском с `@param`, `@returns`, `@example` (язык комментариев — русский, см. AGENTS.md раздел 4) — пример кода обязателен
- Дополнительно — tsdoc рендерится в API ref, поэтому пиши так, чтобы было понятно без чтения исходников
- `src/docs/api-reference.md` — новый публичный метод/опция ядра описывается там всегда, одного JSDoc недостаточно
- `src/docs/GUIDE.md` — если фича заметная (новый сценарий для пользователя фреймворка)
- `src/docs/configuration.md` — если появилась опция конфига, токен или env-переменная

Если меняешь дефолт или сигнатуру — погрепай доки на старое значение/имя и поправь все места, а не только очевидное. Документ, который ты сознательно не тронул, назови в отчёте с причиной.

### Шаг 6: CHANGELOG

Секцию выбирай по правилам AGENTS.md (раздел 6): `[Unreleased]` не использовать; если верхняя секция ещё не выпущена (без даты, с будущей датой или равна версии из `package.json`) — писать в неё, дубликат секции не создавать; если такой секции нет — спросить у пользователя номер версии и срок релиза и дождаться ответа.

Если изменение:

- Добавляет новую возможность → секция `Добавлено`
- Меняет поведение → секция `Изменено`
- Чинит баг → секция `Исправлено`

Breaking changes — конвенция проекта (Keep a Changelog: breaking должно быть «painfully clear»): отдельная секция `### Миграция с X.Y.z` вверху релиза + ссылки «(См. «Миграция с X.Y.z»)» у соответствующих пунктов `Изменено`; сам пункт полезно дополнительно пометить `**[Breaking]**`.

Формат (примеры из реального CHANGELOG 3.1.0):

```markdown
- **Bot**: `addForm()` — новый метод для многошаговых форм...
- **Telegram**: автоматический `parse_mode` отключён (См. «Миграция с 3.0.x»).
```

## Архитектурные правила для core/

1. **Bot.ts** — это фасад. Он НЕ должен содержать:
    - Прямую работу с HTTP (это WebhookServer в будущем)
    - Логику regexp (это CommandReg)
    - Платформенные форматы (это plugins/platforms/\*)
2. **AppContext** — единственный владелец состояния. Никаких глобальных мутаций вне его.
3. **Interfaces** — readonly, никогда не экспортируй class с state.
4. **Timing**: фоновые/отложенные `setTimeout`/`setInterval` — всегда `.unref()`, иначе процесс не выйдет. Исключение — awaited-таймеры, которые обязаны удерживать event loop до своего срабатывания (например, задержка в graceful shutdown перед `process.exit(0)`) — им `.unref()` не нужен.
5. **Память**: любое накапливаемое состояние (Map userId → что-либо, кэши) обязано иметь лимит размера и вытеснение неактивных записей. Образец стандарта — `MAX_STATE_MAP_SIZE` + `evictEntry` + пометка `dead` в `src/middleware/rateLimiter.ts`. Ключи с `userId` attacker-controlled на платформах без подписи вебхука (Алиса/Маруся/SmartApp) — неограниченная Map это DoS-вектор: уникальный `user_id` в каждом запросе выращивает память без лимита.

## Что смотреть при ревью core-изменений

1. Не добавил ли автор `any`?
2. Правильно ли используется `#field` (не просто `_field`)?
3. Есть ли тесты?
4. Осталась ли BC?
5. Ограничено ли новое накапливаемое состояние (лимит Map + вытеснение, см. правило 5 выше)?
6. Lint: 0 errors? Prettier: clean? Build: clean?
7. Документация обновлена (JSDoc + `src/docs/` по карте AGENTS.md раздела 6)?
8. CHANGELOG обновлён, и запись попала в правильную секцию (не `[Unreleased]`)?

## Когда стоп

**ОСТАНОВИСЬ и спроси пользователя**, если:

- Требуется заменить `export *` на именованные экспорты или иначе изменить состав экспортов (в `src/index.ts` только `export *`; прецедент именованных экспортов — CommandReg в `src/core/index.ts`)
- Изменение касается `IPlatformAdapter` или другого публичного интерфейса/экспортируемого класса (включая публичные поля `AppContext` — это тоже публичная поверхность)
- Ты планируешь менять поведение команд (например, `_getCommand` priority)
- Ты хочешь удалить публичный метод
