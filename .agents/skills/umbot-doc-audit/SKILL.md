# Аудит и рефакторинг документации

Глубокий аудит, рефакторинг и стандартизация документации проекта `umbot` — Markdown-файлы и JSDoc-комментарии в исходниках.

## Назначение

Сделать документацию технически точной, согласованной с реальным кодом и API платформ, полезной разработчикам и обрабатываемой ИИ-агентами. Убрать воду, устранить противоречия, закрыть пробелы.

## Контекст

- **Проект**: `umbot` — TypeScript-фреймворк для кроссплатформенных чат-ботов (Алиса, Маруся, VK, MAX, Telegram, Viber, SmartApp).
- **Архитектура**: расширения реализуют `IPlugin`/`IPluginFn` и подключаются через `bot.use()`. DB- и платформенные адаптеры — специализированные плагины.
- **Источник истины**:
    - `src/` (исходный код). Код всегда авторитетен.
    - `cli/` и `cli/template/` — когда документация описывает генерацию проектов, Docker, облачный деплой, токены, генерируемые HTTP-запросы или `flow.json`.
    - `tests/` — только если не уверен в поведении или API.
    - `CHANGELOG.md` — перечень того, что обязано быть задокументировано (Шаг 0.1). Сам он не источник истины о поведении: может отставать от кода или описывать его неточно — сверяй с `src/`.
    - `benchmark/` — код не читать (экономия токенов); исключение — если аудит начат с `src/docs/BENCHMARKS.md` и для сверки нужны факты из `benchmark/`.
- **Платформы**: любая платформенная информация (лимиты, форматы, специфика API) обязана строго соответствовать официальной документации и матрице платформ в AGENTS.md (раздел 9).
- **Репорты — гипотезы**: утверждение пользователя о состоянии документации («доки устарели», «там нет X») — не факт, а гипотеза. Проверяй grep'ом по `src/` и `src/docs/` до вывода; если репорт ложен — фиксируй в «Проверено OK» с фактами, а не начинай правки.
- **Пост-обработка**: финальная документация проходит внешнюю SEO-обработку (title, description, meta-теги). Пиши чистый Markdown без кастомных HTML-обёрток, которые могут сломать внешние SEO-парсеры.

## Воркфлоу

### Шаг 0: аудит и план (до любых правок)

**НЕ ВНОСИ ПРАВКИ.**

1. Проанализируй рабочее пространство. Найди все MD-файлы и JSDoc-блоки в `src/` и корне проекта.
2. Выполни сверку с CHANGELOG (Шаг 0.1) — она обязательна и не пропускается.
3. Подготовь отчёт аудита в формате ниже.
4. **СТОП — жди подтверждения пользователя «План утверждён»**.

### Шаг 0.1: CHANGELOG как чек-лист пробелов

Типовая причина расхождений — фича приехала в код, а документацию не поправили. CHANGELOG показывает такие пробелы быстрее, чем чтение всего `src/`.

1. Прочитай верх `CHANGELOG.md`: текущую (ещё не выпущенную) секцию и минимум две последних выпущенных. Если аудит заказан «по свежим правкам» — хватит невыпущенной секции и последнего релиза.
2. Выпиши каждый пункт `Добавлено` / `Изменено` / `Исправлено` / `Безопасность`, который меняет видимое пользователю фреймворка поведение: новый метод, новая опция, новая env-переменная, новое событие, изменение дефолта, новый лимит платформы, новая команда CLI.
3. Для каждого пункта определи по карте документации из AGENTS.md (раздел 6), где он обязан быть описан, и проверь grep'ом по `src/docs/`, `README.md` и JSDoc в `src/`.
4. Классифицируй результат:
    - **Пробел** — в CHANGELOG есть, в документации нет вообще. Критичный приоритет.
    - **Расхождение** — описано, но описание противоречит коду (старый дефолт, старая сигнатура, старый лимит). Критичный приоритет.
    - **Частично** — упомянуто не там, где читатель будет искать (например, есть в `GUIDE.md`, но нет в `api-reference.md`). Высокий приоритет.
    - **Покрыто** — фиксируй в «Проверено OK», чтобы не перепроверять повторно.
5. Пункт CHANGELOG — гипотеза о коде, а не истина. Прежде чем писать доку по нему, подтверди поведение в `src/`: код авторитетнее CHANGELOG.
6. Обратная сверка: фича, найденная в коде, которой нет ни в документации, ни в CHANGELOG, — тоже находка. Документацию правь, а `CHANGELOG.md` сам **не трогай**: предложи текст пункта и целевую секцию по правилам AGENTS.md (раздел 6) — `[Unreleased]` не использовать, подходящей секции нет → спросить у пользователя версию и срок релиза.

### Шаг 1: итеративный рефакторинг (по одному файлу за раз)

После подтверждения:

- Чини **один файл/модуль за раз**.
- Внеси правки и жди команды «Дальше», прежде чем переходить к следующему файлу.
- Если нужны точные лимиты API (Алиса, VK и т.д.) — найди их через web search по официальной документации. Если не нашёл — помечай `[ТРЕБУЕТ ПРОВЕРКИ]`, не выдумывай числа.

### Шаг 2: разделение форматов (DRY)

- **JSDoc**: только сухие факты для тултипов IDE (сигнатуры, краткое описание, `@param`, `@returns`).
- **Markdown**: архитектурный смысл, «почему», большие примеры. Не дублируй MD в JSDoc.
- Язык JSDoc и документации — русский (см. AGENTS.md раздел 4).

### Шаг 3: оптимизация контента и заполнение пробелов

- **Не добавляй** воду и очевидное (базовый синтаксис TS/JS, как работает npm, async/await, типы string/number).
- **Не удаляй** существующие объяснения базовых концепций, если они помогают понять специфику фреймворка.
- Добавляй недостающие разделы: обработка ошибок, жизненный цикл запроса, кэширование (`Preload`), strict-режим (`strict_prod`), тестирование (`BotTest`), метрики.
- Документируя CLI-генерируемые проекты, сверяй примеры с `cli/flowGenerator.js` и `cli/template/`. Не документируй сгенерированный `fetch` без таймаута, plaintext-токены в коммитоспособных файлах или молчаливую перезапись.
- Структурируй для быстрого онбординга: Quick Start → Архитектура → Базовые концепции → Платформенные/DB-адаптеры → Тестирование → Производительность → FAQ/Рецепты.

### Шаг 4: человеко-ориентированность и польза

- Документация обязана быть одинаково полезной и понятной и людям, и ИИ-агентам.
- Повествование — **для человека** (обращение к разработчику, логические переходы, примеры из реальной жизни).
- **Запрещено**: мета-фразы вида «Если вы агент...», «Для ИИ-ассистентов...», «При обработке этого файла нейросетью...».

### Шаг 5: итеративная верификация (ОБЯЗАТЕЛЬНА)

После всех правок выполни **минимум 2 раунда повторного аудита** — разные аспекты в каждом (например: первый — примеры кода, второй — точность API; при необходимости третий — форматирование).

- Если раунд нашёл проблемы — чини и запускай следующий (пока не получишь чистый раунд).
- Останавливаться можно только после **чистого раунда**, но минимум из двух раундов всегда выполняется.

## Формат отчёта аудита

```markdown
## ОТЧЁТ АУДИТА ДОКУМЕНЦИИ

### Сверка с CHANGELOG (что уехало в релиз без документации)

| Пункт CHANGELOG (секция → запись) | Где обязано быть описано | Статус                               | Проверено                         |
| --------------------------------- | ------------------------ | ------------------------------------ | --------------------------------- |
| [3.1.2] → Добавлено → «…»         | `src/docs/…`             | пробел / расхождение / частично / OK | grep `…` по `src/docs/` — 0 совп. |

Каждый «пробел» и «расхождение» дублируется ниже отдельным пунктом с фиксом.

### Критично (обязательно к фиксу)

1. **[файл:строка]** — описание проблемы
    - **Что не так**: точное описание
    - **Impact**: как это влияет на разработчиков
    - **Фикс**: что нужно изменить

### Высокий (следует починить)

2. ...

### Средний (хорошо бы починить)

3. ...

### Низкий (косметика)

4. ...

### Проверено OK (без проблем)

- JSDoc `src/core/Bot.ts` — точен, соответствует коду
- `src/plugins/platforms/Telegram/Adapter.ts` — лимиты платформы корректны
```

### Определения приоритетов

| Приоритет     | Определение                                                                     | Пример                            |
| ------------- | ------------------------------------------------------------------------------- | --------------------------------- |
| **Критичный** | Пример кода не компилируется, информация об API неверна, противоречит исходнику | Неверная сигнатура метода в JSDoc |
| **Высокий**   | Отсутствует важный раздел, несогласованная терминология между файлами           | Разные имена одной концепции      |
| **Средний**   | Устаревший пример, неоптимальная структура, мелкие противоречия                 | Ссылка на старую версию API       |
| **Низкий**    | Форматирование, стилистическая несогласованность, опциональные детали           | Сломанная таблица markdown        |

## Стандарты качества

- [ ] **Точность**: 100% соответствие реальному коду и официальным API платформ.
- [ ] **Полнота по CHANGELOG**: каждый пункт текущей и последних выпущенных секций CHANGELOG, меняющий видимое поведение, отражён в документации (или явно отклонён с причиной).
- [ ] **Согласованность**: единая терминология, без дубликатов, без конфликтов MD ↔ JSDoc.
- [ ] **Практическая ценность**: разработчик может скопировать пример, запустить и получить результат. Объясняет «почему» и «как», а не только «что».
- [ ] **Читаемость**: понятна джуну с базовым знанием TS, без пережёвывания очевидного. Написано для людей.
- [ ] **Безопасность и best practices**: акцент на `strict_prod`, скрытие токенов, `MongoAdapter` для прода, защита от ReDoS, таймауты голосовых платформ.
- [ ] **Чистый формат**: чистый Markdown, готовый к автоматической SEO-обработке без поломки парсеров.
- [ ] **Без слепого копирования**: никогда не копируй сигнатуры методов/интерфейсов из других MD-файлов (GUIDE.md, FAQ.md) без проверки реального кода в `src/`.

## Правила вывода

1. **СКОУП (КРИТИЧНО)**:
    - Можно править **только** строки с комментариями (`//`, `/* */`, `/** */`) и `.md`-файлы.
    - **ЗАПРЕЩЕНО** менять код (`.ts` вне комментариев): типы, сигнатуры, логику, имена переменных. Если код сломан — не чини его, поставь комментарий `// TODO: [описание проблемы]`.
    - `CHANGELOG.md` — вне скоупа правок этого скилла: недостающие пункты предлагай пользователю текстом, секцию и срок релиза уточняй по AGENTS.md разделу 6.
2. **Без воды**: не пиши вступлений вроде «Отлично, я проанализировал код, вот мои правки». Применяй фиксы напрямую.
3. **Вопросы**: если не уверен в поведении платформы — **останови выполнение** и спроси в чате.
4. **Без повторов**: не репортируй заново уже отклонённые находки. Веди трекинг проверенного.

## Чек-лист самопроверки

### После КАЖДОГО изменения файла:

- [ ] Перечитай изменённый раздел — подтверди: нет дубликатов, форматирование корректно.
- [ ] Если менял пример кода — проверь, что все импорты на месте и переменные объявлены.

### При работе с API-документацией:

- [ ] **НИКОГДА не копируй сигнатуры из GUIDE.md** — GUIDE упрощает для читаемости. Всегда сверяй с реальным кодом в `src/`.
- [ ] Для каждого метода в таблице: проверь имя метода, типы параметров, тип возврата по исходнику.
- [ ] Проверь, что все опциональные параметры помечены как опциональные (`?`).

### При написании примеров кода:

- [ ] Каждый пример обязан компилироваться «как есть» — все импорты, все типы, все переменные.
- [ ] Не используй плейсхолдеры вроде `handler` без определения — пиши inline-функции.
- [ ] Проверь регистр строковых литералов (особенно в слотах команд — они регистрозависимы).

### При форматировании:

- [ ] Проверь, что markdown-маркеры `**` не разорваны переносами строк.
- [ ] Проверь пробелы перед скобками: `ресурс (описание)`, не `ресурс(описание)`.
- [ ] Проверь, что во всех таблицах одинаковое число колонок в шапке и строках.

### Финальная проверка:

- [ ] Перепроверь список из Шага 0.1: каждый пробел закрыт правкой либо явно отклонён с причиной.
- [ ] Пройди по каждому изменённому файлу и сверься с исходником (`src/`).
- [ ] Проверь, что примеры кода рабочие и используют актуальный API.
- [ ] Подтверди: текст для людей, без «обращений к ИИ».
- [ ] Не удалил полезные объяснения, заменив их «очевидными» фактами.
- [ ] Описания платформ соответствуют их реальным API.
- [ ] Прогнал `npm run build` — TypeScript компилируется без ошибок.

## Старт

Твоя первая и единственная задача сейчас — выполнить **Шаг 0** вместе со сверкой с CHANGELOG (**Шаг 0.1**). Подготовь отчёт аудита и **СТОП**. Не применяй фиксы, пока пользователь не ответит «План утверждён».
