# Fix Bug: скилл для исправления бага в umbot

## Назначение

Стандартный процесс для исправления бага — от воспроизведения до закрытия с тестом. Главное правило: **не правь без воспроизводящего теста**.

## Триггер

- "обнаружил баг"
- "в проде падает X"
- "нужен фикс для Y"

## Воркфлоу

### Шаг 0: Воспроизведение (обязательно)

Напиши **минимальный** тест, который падает с тем же сообщением/поведением, что в багрепорте. Если не получается — спроси у репортера дополнительный контекст.

Если баг в platform adapter — мокай HTTP-вызовы (в шапке файла теста, до импортов, объявляется `global.fetch = jest.fn();`):

```ts
global.fetch = jest.fn();
// ...импорты...
(global.fetch as jest.Mock).mockResolvedValueOnce({
    ok: true,
    json: async () => ({ ok: true, result: { message_id: 1 } }),
});
```

Если баг в engine — используй `bot.run`. Обязательный минимум: stub логгер + `initBotController` + адаптер платформы. В тестах репо импорты идут из `'../../src'` / `'../../src/plugins'` (импорты `'umbot'` — self-reference, требуют собранного `dist/` — так не делают); сниппет ниже приведён к этому паттерну:

```ts
import { Bot, BaseBotController } from '../../src';
import { AlisaAdapter, T_ALISA, IAlisaWebhookResponse } from '../../src/plugins';

const bot = new Bot();
const errorLogs: string[] = [];
bot.setLogger({ log: () => {}, error: (msg) => errorLogs.push(String(msg)), warn: () => {} });
bot.initBotController(BaseBotController);
bot.addCommand('hello', ['привет'], (_, ctx) => {
    ctx.text = 'Салют!';
});
bot.use(new AlisaAdapter());

const query = JSON.stringify({
    meta: { locale: 'ru-Ru', timezone: 'UTC', client_id: 'test', interfaces: {} },
    session: {
        message_id: 1,
        session_id: 'local',
        skill_id: 'local',
        user_id: 'test_user',
        new: false,
    },
    request: { command: 'привет', original_utterance: 'привет', nlu: {}, type: 'SimpleUtterance' },
    state: { session: {} },
    version: '1.0',
});

const result = (await bot.run(T_ALISA, query)) as IAlisaWebhookResponse;
expect(result.response?.text).toBe('Салют!');
```

Если репорт вида «в логах ошибка» (фреймворк что-то пишет в лог, а не падает) — минимальное воспроизведение другое: **перехват лога** через stub-логгер с захватом сообщений (как в сниппете выше — `errorLogs.push(msg)`) + действие, которое его вызывает (например, `bot.addCommand('x', [/(a+)+/], noop)` для ReDoS-сообщений). Образец — хелпер `captureRegexLog` в `tests/Bot/bot.test.ts` (~строка 1255) и тесты `redos error` (~строки 1316–1334).

Полный паттерн integration-теста с хелпером `getContent()` — в `umbot-write-tests` (раздел Integration-тесты) и `tests/Bot/bot.test.ts`.

### Шаг 1: Поиск первопричины (root cause)

Найди **истинную причину**, а не симптом:

- Trace до первого вызова, который возвращает неправильное значение.
- Проверь: это баг логики или баг контракта (например, формат платформы против API)?
- Это regress от предыдущего фикса? Если да — откат или корректируй.

**Не правь пока не найдена причина.**

### Шаг 1.1: «А ошибка ли это вообще?» (скептический анализ)

Сообщение об ошибке — это гипотеза, а не факт. Прежде чем чинить, разбери репорт по вариантам:

1. **Ожидаемое поведение за флагом.** «X не работает», но X работает только при включённой опции (`isLocalStorage`, `strict_prod`, лимиты адаптера и т.п.). Проверь конфиг воспроизводителя — если опция выключена, это не баг кода. Возможны два исхода:
    - поведение корректно задокументировано → закрой репорт как «works as designed», объясни, какую опцию включить;
    - из доки не следует, что нужна опция, или поведение молча отличается → это **баг документации**: правь доку (+ CHANGELOG, секция «Документация»), не код.
2. **Ожидаемое поведение по контракту платформы.** «Кнопки не приходят» — а платформа их не поддерживает в этом режиме (screens-off у Алисы, лимит ряда у MAX/Viber). Сверься с матрицей платформ (AGENTS.md, раздел 9) — возможно, это корректная деградация.
3. **Ловушка окружения, не кода.** Токен не задан в env, порт занят, `./json`/`./logs` не созданы, файлы от предыдущего запуска (FileAdapter state). Проверь чистоту окружения воспроизводителя, прежде чем винить код.
4. **Тест фиксирует не то поведение.** Если падает существующий тест — прочитай его намерение: возможно, он проверял артефакт реализации, а не контракт, и править надо тест (осознанно, с объяснением в PR).
5. **Несуществующий сценарий.** Запрос, который реальный вебхук платформы никогда не пришлёт (самодельный payload без обязательных полей). Тогда вопрос — должна ли валидация отвечать на него ошибкой, и если да — это фича-запрос, не баг.

Вердикт обязательно зафиксируй в отчёте: `bug` (чиним по шагам ниже), `works-as-designed` (закрываем с пояснением), `doc-bug` (правим документацию), `test-bug` (правим тест). Если после разбора остаётся двусмысленность — остановись и спроси пользователя, а не выбирай вариант молча.

### Шаг 2: План

Коротко:

- Какой файл правим
- Какой метод
- Что меняем
- Какой контракт сохраняем
- Есть ли риск breaking change

### Шаг 3: Фикс

Внеси изменение. Проверка:

- Код читается (соблюдает code-style)
- Нет новых `any`
- Все async с `await` или `.catch()`
- Логи не содержат чувствительных данных (токены, пароли)

### Шаг 4: Тесты

1. Воспроизводящий тест ТЕПЕРЬ должен проходить
2. smoke-прогон: все существующие тесты зелёные
3. Если исправил граничный случай — добавь unit-test именно на него

### Шаг 5: Верификация

```bash
npm run build
npm run test
npm run prettier
npm run lint
```

### Шаг 6: Документация

- Если сломанное поведение описано в документации или фикс меняет описанное поведение (дефолт, лимит, сигнатуру, текст ошибки) — поправь `src/docs/` по карте из AGENTS.md (раздел 6). Фикс без правки устаревшего описания просто переносит баг в документацию.
- Если фикс добавил новую опцию или новую защиту — это новая фича: документируется наравне с кодом.
- CHANGELOG.md → секция `Исправлено` (или `Добавлено`, если фикс добавляет новую защиту). Целевую секцию выбирай по AGENTS.md разделу 6: `[Unreleased]` не использовать; верхняя невыпущенная секция (без даты / с будущей датой / равная версии из `package.json`) — целевая; если её нет — спроси у пользователя версию и срок релиза.
- Комментарий в коде с **причиной**: "Fix: <почему это было сломано>"

## Когда стоп

- Баг в публичной API signature → остановись, спроси.
- Баг связан с несколькими платформами → проверь, что фикс один и тот же для всех, или что он в правильном месте.
- Фикс требует изменить поведение, которое #other-feature зависит → обсуди Trade-off.

## Критерии успеха

1. ✅ Падающий тест восстановлен
2. ✅ Новые тесты есть
3. ✅ Build green
4. ✅ Все тесты green
5. ✅ Lint clean
6. ✅ Документация поправлена, если фикс менял описанное поведение
7. ✅ CHANGELOG обновлён (секция по AGENTS.md разделу 6, не `[Unreleased]`)
