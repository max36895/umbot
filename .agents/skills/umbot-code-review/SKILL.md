# Code Review: ревью диффа или PR в umbot

## Назначение

Ревью **конкретных предложенных изменений** (uncommitted diff, PR, коммит) перед мержем. Отличие от сиблингов:

- **`umbot-code-audit`** — проактивный поиск багов по всему `src/`+`cli/` без конкретного диффа. Здесь — только то, что менялось.
- **`umbot-platform-code-audit`** — то же, но только слой платформенных адаптеров.
- **`umbot-fix-bug`** — ты сам чинишь баг. Здесь — ты смотришь на чужой/свой готовый фикс.

## Вход

Дифф, который ревьюишь: `git diff` / `git diff --cached` / `git diff main..HEAD` / конкретные файлы из задачи. Если диффа нет и задача «найди баги в проекте» — это не этот скилл, бери `umbot-code-audit`.

## Воркфлоу

### Шаг 1: Карта изменений

Собери контекст: какие файлы, какие функции, что добавилось/удалилось. Раздели изменения на категории:

- правки ядра (`src/core/`) — самый высокий риск
- правки платформенных адаптеров (`src/plugins/platforms/`)
- правки публичного API (экспорты `src/index.ts`, `src/plugins.ts`, `src/middleware.ts`, сигнатуры)
- тесты
- документация/CLI

⚠️ Если правится публичный API (сигнатура, удаление экспорта, поведение по умолчанию) — это **блокер до обсуждения с автором**: по AGENTS.md (раздел 2) это breaking change, требующий major + осознанного решения.

### Шаг 2: Ревью по чек-листу (для каждой изменённой строки)

Прочитай дифф строку за строкой, но **окружение — из полной версии файла**, не из диффа (дифф обрезает контекст и легко скрывает, что переменная уже переопределена выше).

**Корректность:**

1. Логика в новых ветках (`if`/`switch`/`try`) — что происходит на каждой ветке, включая граничные значения (пустая строка, 0, `null`/`undefined`, большие лимиты платформ).
2. Все Promise обработаны: `await` или `.catch()`; fire-and-forget запрещён (AGENTS.md раздел 4). ⚠️ `await` без `try/catch` — тоже пробел в тех точках, где rejection обязан превратиться в HTTP-ответ платформе (`webhookHandle`, обработчики вебхуков): упавший await → платформа без ответа → на 5xx ретраи/отключение вебхука. Линтер (`no-floating-promises`) этот случай не ловит — awaited-промис «обработан».
3. Результат `Request._getOptions()` проверяется перед `fetch` (`undefined` при ошибке attach → паразитный GET).
4. `new RegExp`/компиляция регулярки не в hot-loop (кэш — `Text.ts`/`RegExp.ts`; ReDoS-паттерны типа `(a+)+` не вводятся).
5. `setTimeout`/`setInterval` с `.unref()`; таймеры/слушатели, добавленные диффом, — очищаются (`destroy*`, `clearInterval`), иначе процесс не выйдет (AGENTS.md раздел 10, анти-паттерн 2). ⚠️ Оговорка: awaited-таймеры, удерживающие event loop до срабатывания (graceful shutdown), `.unref()` не требуют.

После чек-листа прогони линтер — он ловит часть пунктов автоматически, но с оговорками. Правила проекта (`eslint.config.js`, основной блок `**/*.ts`, все в `error` кроме `no-explicit-any` в `warn`): `no-floating-promises`, `no-misused-promises`, `await-thenable`, `require-atomic-updates`, `ban-ts-comment` (запрет `@ts-ignore`), `detect-unsafe-regex`. **Overrides**: в `tests/**` отключены `require-atomic-updates`/`await-thenable`/`no-misused-promises`/`no-floating-promises`, в `cli/**` — `await-thenable`/`no-misused-promises`/`no-floating-promises` (`detect-unsafe-regex` в cli работает). Для диффов в тестах и CLI автоматической подстраховки пунктами 2–5 нет — проверяй вручную. Красный lint — блокер ревью, не «починим потом».

**Инварианты архитектуры (AGENTS.md раздел 2):**

6. Направление зависимостей: `core/`/`components/` не импортируют из `plugins/`.
7. Инкапсуляция: внутреннее состояние — `#field`, не `_field`.
8. Не появилось `any`, `@ts-ignore`, `eval`/`new Function`.
9. `ctx.userData` не переприсваивается целиком (`= {...}`) — только merge по ключам.
10. `ctx.requestObject` не мутирует.
11. Логи не содержат секретов в открытом виде; кастомный логгер по умолчанию маскирует (включая вложенные метаданные), `maskSecrets: false` — только осознанно. Не путай уровни: `AppContext.log()` вообще не маскирует (операционные сообщения), маскируют `logError`/`logWarn`/`logMetric`. Отдельно от секретов — attacker-controlled НЕ-секретные данные (например `user_id` с неподписанных платформ, AGENTS.md 9.1): интерполировать их в лог можно как ключ/идентификатор, но нельзя строить на них решения безопасности; классифицируется как «инъекция в логи», а не «утечка секрета».

**Платформенные и путь запроса (если затронуты адаптеры или `webhookHandle`/HTTP-слой):**

12. Контракт формата против официального API (кнопки/карточки/лимиты) — см. `umbot-platform-code-audit`.
13. `button.options` — доступ через `?.`/`?? {}`.
14. Служебные события → `skipAutoReply`, не `setQueryData() === false`.
15. Ответы платформе — HTTP 200 даже на неизвестные события — правило касается ЛЮБОГО кода в пути запроса (адаптеры, `Bot.webhookHandle`, middleware-цепочка), не только адаптеров: на 5xx Telegram повторяет апдейт бесконечно, VK отключает сервер, Viber не регистрирует вебхук (AGENTS.md 9.1).

**Тесты:**

16. Новые ветки/методы покрыты; воспроизводящий тест для багфикса существует и падает без фикса.
17. Тесты изолированы: логгер stub, fetch mock, БД не на диске; env-переменные токенов не утекают (см. `umbot-write-tests`).
18. Тест не зависит от порядка других тестов.

**Документация (ревьюится так же строго, как код):**

19. Публичный метод/опция → JSDoc на русском с `@param`/`@returns`/`@example`.
20. Новая фича / новая опция / изменение дефолта / новая env-переменная / новая команда CLI → дифф обязан содержать правки `src/docs/` (и `README.md`, если фича видна там) по карте из AGENTS.md (раздел 6). Дифф с новой функциональностью и без документации — **REQUEST CHANGES**, а не «замечание на будущее»: именно так фичи уезжают в релиз недокументированными.
21. Изменение дефолта, сигнатуры или лимита → погрепай доки на старое значение: не осталось ли устаревшего описания в файлах, которых дифф не касался.
22. Новая фича / изменение поведения / критический фикс → запись в CHANGELOG (русские секции: `Добавлено`/`Изменено`/`Исправлено`/`Безопасность`) в секцию по правилам AGENTS.md раздела 6. Запись в `[Unreleased]` или новая секция версии, созданная без согласования срока релиза с пользователем, — замечание ревью.
23. Платформенные лимиты/новая платформа → матрица в AGENTS.md (раздел 9).

### Шаг 3: Скептический фильтр (обязателен)

Каждая находка проходит самопроверку, прежде чем попасть в отчёт:

1. **Прочитай полную функцию** — меняет ли контекст интерпретацию?
2. **Кто вызывает этот код?** Недостижимый в проде путь — не находка.
3. **Есть ли причина, почему так написано?** (BC публичного API, специфика платформы из AGENTS.md 9–9.1, документированное поведение).
4. **Можно ли отклонить находку конкретной причиной?** Если да — она в блок «Отклонено», не в основные.

Не выдавай «на всякий случай» замечания о стиле, если они не влияют на корректность/безопасность/производительность — их игнорируют, и это разлагает доверие к ревью в целом.

### Шаг 4: Вердикт + отчёт

Формат отчёта:

```markdown
## РЕВЬЮ: <краткое описание диффа>

### Вердикт: APPROVE / REQUEST CHANGES / BLOCKED (публичный API без согласования)

### Блокирующие (нельзя мержить)

1. **[файл:строка]** — что не так, почему это сломается (конкретный сценарий), как исправить.

### Желательные (можно отдельным PR)

2. ...

### Отклонено (проверил, не проблема)

- `src/...` — читается как X, но на самом деле Y, потому что Z.
```

Каждый пункт: где (файл:строка), что случится (сценарий, не «может быть проблема»), как чинить. Устно предложить «лучше переписать» без сценария поломки — не находка.

После решения автора о мерже: если правки вносятся — прогон в порядке проекта `npm run build` → `npm run test` → `npm run prettier` → `npm run lint`.

## Анти-паттерны ревьюера

- ❌ Ревьюить только дифф без чтения полной версии файла — контекст обрезан.
- ❌ Требовать рефакторинга работающего кода «заодно» — ревью про изменения, а не про вкусы.
- ❌ Игнорировать тесты («сами разберутся») — тестовая логика ревьюится так же строго, это код, который будет врать при регрессии.
- ❌ Одобрять дифф с красным lint/build «чтобы не задерживать» — блокер.
- ❌ Менять код за автора молча: ревью — это отчёт; правки — только по явной просьбе пользователя.
