# Аудит кода: security, производительность, архитектура

Senior-уровень аудит `umbot`: поиск реальных проблем и их фикс. Никакой косметики ради косметики.

## Назначение

Провести глубокий аудит кода `umbot`, найти реальные проблемы и исправить их. Ключевой принцип — **Senior Review**: каждая находка проходит внутреннюю самопроверку. Жаловаться ради жалоб запрещено. Если проблема не влияет на security, производительность или прод-стабильность — её не стоит упоминать.

## Контекст

- **Проект**: `umbot` (TS-фреймворк: Алиса, Маруся, VK, MAX, Telegram, Viber, SmartApp).
- **Архитектура**: плагины (`IPlugin`), `bot.use()`, DB/platform-адаптеры.
- **Источник истины**:
    - `src/` — код (приоритет №1);
    - `cli/` — продуктовый генератор. Сгенерированный TypeScript/шаблоны/конфиги — это прод-код, потому что пользователи запускают его напрямую;
    - `tests/` — только для сверки ожидаемого поведения (если код противоречит тесту — это баг, спроси пользователя);
    - `benchmark/` — не трогать.
- **Enterprise-контекст**: библиотека для банков и госсектора. Приоритеты: Security > Стабильность > Производительность > Чистота кода.
- **Игнорировать**: комментарии и Markdown-документацию (их чинит другой скилл — `umbot-doc-audit`).

## КРИТИЧНО: приоритетный порядок аудита

Аудит обязан идти в этом порядке. Не пропускать уровни.

### Приоритет 1: платформенные адаптеры (самое критичное)

**Источник багов №1 в проде.** Каждый адаптер сверяется с РЕАЛЬНЫМ API платформы.

Для КАЖДОЙ платформы (Telegram, VK, Алиса, Маруся, MAX, Viber, SmartApp):

1. **Формат ответа**: возвращает ли `getContent()` ровно ту JSON-структуру, которую ждёт API платформы?
2. **Формат кнопок**: имена полей, типы, вложенность корректны? (например, Telegram требует `InlineKeyboardButton[][]`, не плоский `InlineKeyboardButton[]`)
3. **Формат карточек/медиа**: корректны ли форматы изображений, аудио, каруселей?
4. **API-запросы**: корректны ли URL методов, HTTP-методы, имена параметров, авторизация?
5. **Поток данных**: трассируй путь `CardContent` → `cardProcessing()` → API-запрос. Не теряются ли данные молча?

**Как проверять**: читай `Button.ts`, `Card.ts`, `Adapter.ts` адаптера и соответствующий `API/*Request.ts`. Для каждого формата сверяйся с матрицей платформ и разделом «Verified» в AGENTS.md (разделы 9–10.1): имена полей, типы (string vs number vs object vs array), вложенность (массив массивов vs плоский), лимиты (длина caption, число кнопок, размер payload).

### Приоритет 2: движок — резолв команд и поток запроса

Трассируй ТОЧНЫЙ путь запроса (вход и оркестрация — в `src/core/Bot.ts`, сам пайплайн — в `src/controller/BotController.ts`):

```
Bot.webhookHandle() → Bot.run() → adapter.setQueryData() → Bot.#runApp()
    → BotController.run() (src/controller/BotController.ts)
        ├── #eventResolver()          — служебные события платформы
        └── #runPipeline()
            ├── #stepResolver()       — шаги (forms)
            ├── _getCommand()
            │   ├── #getExactCommand()
            │   ├── #sendCustomCommandResolver() → appContext.command.customCommandResolver
            │   └── loop: commands → #searchCommandsInGroup() / Text.isSayText()
            └── #runIntentOrFallback()
                ├── _getIntent()
                └── fallback-команда ("*")
```

Для каждого шага проверяй:

- Что происходит, если колбэк async? Используется ли `await` корректно?
- Что происходит, если колбэк бросает? Перехватывается ли ошибка?
- Что происходит, если колбэк возвращает `false`, `null`, `undefined` или значение?
- Есть ли race conditions в доступе к shared state?

### Приоритет 3: DB-адаптеры

1. **FileAdapter**: конкурентные записи, целостность данных при shutdown, файловые локи (документирован как single-process — локи не добавлять)
2. **MongoAdapter**: жизненный цикл коннекта, восстановление после ошибок, заполнение `databaseInfo`
3. **Базовый адаптер**: поток save/update/insert, корректность escapeString

### Приоритет 4: всё остальное

- rateLimiter (конкурентность, управление памятью)
- Request.ts HTTP-клиент (таймауты, обработка ошибок)
- CLI-генератор и шаблоны: сгенерированный TypeScript, Dockerfile, облачные конфиги, безопасность перезаписи, обработка токенов
- NLU-обработка
- Sound-обработка
- Компонент Navigation
- Text-утилиты (кэш регулярок, similarity)

### Проверенные точки (аудит 3.1.0 — закрывай их в первую очередь, они уже ловили баги)

- **Request.ts**: `_getOptions()` возвращает `undefined` при ошибке attach — без проверки перед `fetch` уходил паразитный GET к API платформы (фикс в `#run`). `send()` сбрасывает `attach/post/get/customRequest` после вызова; `#error` — `Error | string`, лог-хелперы API-клиентов обязаны принимать оба типа.
- **Метрики**: `logMetric` обязан прогонять имя и label через маскирование (`#maskLogData`) — `Request` кладёт в label URL с токеном Telegram.
- **rateLimiter**: (1) батч из очереди должен проверять `st.count >= limit` перед каждым элементом — иначе окно исполняет до 2×limit; (2) вытесненные записи (`evictEntry`/`destroyRateLimiter`) помечаются `dead`, а `processQueue` в `finally` обязан проверять `!st.dead` — иначе бесконечный перезапуск; (3) переполнение очереди — экспортируемый `RateLimitQueueOverflowError` + флаг `platformOptions.rateLimitOverflow` (ядро перехватывает исключение middleware).
- **ipFilter**: поддержка IPv6 (BigInt, `::`-сжатие, hex-mapped `::ffff:102:304`); строковый срез `::ffff:` — только когда хвост dotted-quad, иначе hex-форма портится; правила сравниваются по версии адреса (v4-правило не матчит v6-клиента).
- **EnvConfig**: `#` без пробела перед ним — часть значения (`pass#word`), инлайн-комментарий — только ` #` (конвенция dotenv, quote-aware).
- **isRegexLikelySafe**: опасны квантифицированные группы с квантификатором, альтернативой или `.` внутри (`(a+)+`, `(a|aa)+`, `(?:\w+\.)+`); `.*`, `.*.*`, `(abc)+`, `(?:a{2,3})` — безопасны. При анализе тела группы пропускай префикс `(?:`/`(?=`/`(?<name>` — иначе `?` из префикса ложно срабатывает как квантификатор.
- **FileAdapter**: `#isForbiddenKey` (`__proto__`/`constructor`/`prototype`) обязателен и на чтение (`_select`/`#selectInPrimaryKey`), не только на запись/удаление — иначе `content['__proto__']` возвращает `Object.prototype` как «найденную запись».
- **Text.isSayTrue/isSayFalse**: границы слова через lookaround `(?<![a-zа-яё0-9_])`, чтобы распознавать «Да!»/«Нет, спасибо» и не матчить «даже»/«небоскреб».
- **CommandReg/группы**: строковый паттерн группы (fallback при превышении MAX_COUNT_FOR_GROUP) обязан компилироваться через кэш `getGroupRegExpCompiled`, не через `getRegExp` на каждом запросе.
- **CLI**: `spawnSync` с `shell: true` (Windows) склеивает аргументы без экранирования — значения из `.env`/flow.json обязаны квотироваться и санитизироваться; при записи `.env` вырезай `\r\n` из значений; имя проекта, начинающееся с цифры, — префикс `_`.

## Размерности аудита (11 категорий)

Ищи конкретные проблемы, а не общие рассуждения:

1. **SECURITY**: ReDoS (проверь `isRegexLikelySafe`), prototype pollution, утечки токенов в логах (особенно в `strict_prod` и кастомных логгерах), plaintext-секреты в генерируемых файлах (`serverless.yml`, исходники, package.json), инъекции, XSS.
2. **PERFORMANCE**: блокировка event loop (синхронные операции в async), утечки памяти (кэши, таймеры без `.unref()`), O-сложность, HTTP-таймауты. Сгенерированный HTTP-код не должен создавать unbounded `fetch` внутри обработчиков бота.
3. **CONCURRENCY**: race conditions, забытый `await`, некорректный `Promise.all`, доступ к shared state.
4. **RESOURCE MANAGEMENT**: закрытие соединений (Mongo/File), очистка таймеров, стримы, файловые дескрипторы.
5. **ERROR HANDLING**: проглоченные ошибки, крэши, некорректный graceful shutdown.
6. **ARCHITECTURE & API**: SOLID, DRY, скрытая магия, breaking changes, интуитивность API.
7. **TYPESCRIPT**: использование `any`, `@ts-ignore`, нарушения strict mode.
8. **TYPE COERCION**: неявные конверсии с неверным результатом (например, `+""` → `0`, `+undefined` → `NaN`). Проверяй каждую арифметическую операцию и сравнение значений из парсинга.
9. **EDGE CASES IN PARSING**: `JSON.parse` без try/catch, граничные случаи regex (пустые строки, спецсимволы), дефолты, которые прячут баги.
10. **REGEX COMPILATION В HOT PATHS**: `new RegExp()` в циклах или per-request методах. Для литеральных замен предпочитай `String.prototype.replaceAll()`, для повторного использования — кэш скомпилированных RegExp.
11. **GENERATED PRODUCT QUALITY**: каждое изменение CLI/шаблонов проверяй как пользовательский код. Он обязан компилироваться со сгенерированным tsconfig, не ломать Docker/cloud-деплой, не перезаписывать файлы молча и не хранить реальные секреты вне игнорируемых локальных файлов.

## Воркфлоу

### Шаг 0: аудит, Senior Review и план (до любых правок)

**НЕ ВНОСИ ПРАВКИ.**

1. **Сбор контекста**: не читай все файлы разом! Сначала изучи структуру `src/`, прочитай точки входа (`index.ts`, `Bot.ts`, `AppContext.ts`). Затем подгружай файлы по мере надобности.
2. **Проверка платформ (приоритет 1)**: для каждого адаптера прочитай реальный файл API-запросов и сверь форматы со спецификациями API. Это самый критичный шаг.
3. **Трассировка async-цепочек (приоритет 2)**: для каждого async-метода трассируй полную цепочку промисов. Ищи забытые `await`, unhandled rejections, race conditions.
4. **Скан hot paths (категория 10)**: поиск `new RegExp(` во всех файлах. Проверь, не в циклах ли и не в per-request методах. Ищи `.replace(new RegExp(`, `.forEach.*new RegExp(`, `Array.sort` в hot paths.
5. **Проверка type coercion (категория 8)**: найди все `+variable` и `Number(variable)` конверсии. Проверь обработку пустых строк и nullish-значений.
6. **Скан CLI/генерируемых проектов**: если задача затрагивает генерируемое поведение — изучи `cli/`, `cli/template/`, `cli/AGENTS.md`, `tests/cli/`. Проверь HTTP-таймауты, безопасную JSON-интерполяцию, Docker-стадии, секреты в облачных конфигах, защиту от перезаписи.
7. **Генерация и самопроверка (Senior Review)**: находи проблемы и **сразу же опровергай их сам**.
    - _Пример_: «Нашёл `readFileSync`. Но это FileAdapter для dev-режима, не hot path. Находка отклонена».
    - _Пример_: «Нашёл, что `getButtonJson` возвращает null. Но, может, это осознанно? Нет — код вызывает его и ждёт string. Находка подтверждена».
8. **Верификация ПЕРЕД отчётом**: для КАЖДОЙ находки выполни ВСЕ проверки, прежде чем включить её в отчёт:
    - **Прочитай окружающий код**: меняет ли контекст интерпретацию?
    - **Проверь вызывающих**: этот код-путь реально достижим в проде?
    - **Оцени impact**: что РЕАЛЬНО ломается? Не «могло бы сломаться» — что СЛОМАЕТСЯ?
    - **Рассмотри альтернативы**: есть ли причина, почему код написан так?
    - **Челленджируй себя**: можешь отклонить находку с конкретной причиной? Если да — отклоняй.
9. **Формирование отчёта**: выводи отчёт в формате ниже. Включай **ТОЛЬКО** находки, которые не смог отклонить после верификации. Отклонённые — отдельным блоком в конце с краткой причиной (1 предложение).
10. **СТОП — жди ответа пользователя "План утверждён"**.

**Формат отчёта:**

```markdown
## ОТЧЁТ АУДИТА

### Подтверждённые находки (требуют фикса)

1. **[Critical] [Platform]** `src/plugins/platforms/Telegram/Button.ts:44` — несовпадение структуры клавиатуры
    - **Описание**: `inline_keyboard` — плоский `[]`, а Telegram API требует `[[]]`.
    - **Impact**: кнопки никогда не отображаются корректно.
    - **Фикс**: обернуть каждую кнопку в собственный массив.

2. **[High] [Concurrency]** `src/core/Bot.ts:1018` — лок DB-коннекта не освобождается
    - ...

### Отклонённые находки (Senior Review)

- `src/utils/standard/Text.ts:112` (readFileSync) — отклонено: не hot path, инициализация на старте.
- `src/core/Bot.ts:88` (тип any) — отклонено: публичный API для кастомных плагинов, strict-типизация ломает BC.
```

### Шаг 1: итеративные фиксы (по одному файлу за раз)

После подтверждения «План утверждён»:

- Чини строго один файл за раз.
- Внеси правку.
- После правки выведи в чат:
    - что изменилось и как это решает проблему;
    - потенциальные побочные эффекты.
- Спроси: «Перехожу к следующему файлу?». Жди команды.
- Если фикс требует изменения публичного API (breaking change) — СТОП и вопрос пользователю.

### Шаг 2: финальная верификация

После всех фиксов прогони проверку в порядке проекта: `npm run build`, затем `npm run test`, затем `npm run prettier`, затем `npm run lint`. Выведи финальный статус: какие находки закрыты, какие остались и почему.

Если фикс изменил задокументированное поведение (дефолт, лимит, сигнатуру, опцию) — документация правится тем же изменением (AGENTS.md раздел 6). Допустимо вынести её в отдельный проход `umbot-doc-audit`, но не оставлять расхождение молча. Пробелы в документации, замеченные по ходу аудита и не связанные с твоими фиксами, не чини здесь — вынеси их отдельным блоком «Документация» в финальный отчёт.

## Правила вывода

1. **СКОУП (КРИТИЧНО)**:
    - Дефолтный скоуп аудита — код в `src/` плюс `cli/`, когда затронуто генерируемое продуктовое поведение. Перед разбором `cli/` прочитай `cli/AGENTS.md` — там список уже закрытых багов генератора, чтобы не репортить их повторно.
    - **ЗАПРЕЩЕНО** менять комментарии, Markdown, тесты ради стиля. НО если фикс бага требует обновить тест, CHANGELOG, AGENTS.md или этот скилл (чтобы не повторять ошибку) — это разрешено после одобрения пользователя.
2. **Без воды**: никаких вступлений. Сразу к делу.
3. **Вопросы**: если не уверен в поведении платформы — останови выполнение и спроси.
4. **Верификация**: каждая находка ОБЯЗАНА быть проверена чтением окружающего кода. Ложные срабатывания тратят время всех и подрывают доверие.
5. **Без повторов**: не репортируй заново находки, уже отклонённые в этой сессии. Веди трекинг того, что проверено и отклонено.
6. **Performance-first**: оценивая находку, спрашивай: «Влияет ли это на производительность измеримо?» Микрооптимизации (< 1 мкс разницы) не стоят изменения.

## Старт

Перед Шагом 0 задай только эти 3 критичных вопроса (если они не очевидны из контекста). Не больше:

1. **Breaking changes**: готов ли я к breaking changes в публичном API ради security/performance, или фиксы должны быть строго обратно совместимы?
2. **Фокус аудита**: есть ли модули для проверки в первую очередь (например, core, адаптеры), или начинать с самого критичного (Security/Performance)?
3. **RegExp**: уделить ли максимум внимания замене стандартных RegExp на re2 везде, где есть пользовательский ввод?

Получив ответы, выполняй Шаг 0. СТОП — жди подтверждения.
