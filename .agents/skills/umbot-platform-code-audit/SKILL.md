# Platform Code Audit: аудит платформенных адаптеров

## Назначение

Дотошный аудит адаптеров платформ (`src/plugins/platforms/`) на несоответствия контрактам официальных API, нарушения форматов и архитектурные проблемы, которые приводят к 4xx от платформ и неработающим кнопкам/карточкам.

Отличие от `umbot-code-audit`: этот скилл сфокусирован на **платформенных контрактах** (кнопки, карточки, медиа, подписи, лимиты), а не на общем коде (security, race conditions, производительность). Если задача шире слоя адаптеров — возьми `umbot-code-audit`.

## Дисциплина верификации (обязательна)

Аудит ценен только подтверждёнными находками. Для каждой находки:

1. **Сверься с официальной документацией платформы** (web search, если доступен в сессии). Знания модели об API могли устареть — память не считается подтверждением.
2. **Прочитай окружающий код**: пути вызова, кто вызывает метод. Находка, до которой прод не доходит, — не находка.
3. **Провери тесты**: если тест фиксирует текущее поведение как ожидаемое — возможно, это осознанное решение, а не баг.
4. **Отмечай уровень уверенности явно**: `confirmed` (дока + код), `likely` (код противоречит известному формату, но доку не сверял), `needs-verification` (свериться не удалось). Не выдавай `likely` за `confirmed`.

Неподтверждённые пункты идут в отдельный блок «Требует ручной проверки» с указанием, что именно проверить, — а не в основной отчёт.

## Воркфлоу

### Шаг 0: Разведка (без правок)

Изучи архитектуру: `BasePlatform` (`platforms/Base/Base.ts`), обработчики (`buttonProcessing`, `cardProcessing`, `soundProcessing`), API-классы (`platforms/API/*Request.ts`). Сформируй карту: что общее, что платформоспецифичное.

Выведи короткое резюме: архитектура, список адаптеров в зоне аудита, предварительные зоны риска. **STOP — жди реакции пользователя** («ок», «давай план»).

### Шаг 1: Детальный аудит + план

Аудируй по правилам раздела «Что ищем». Каждая находка проходит дисциплину верификации и оформляется строго:

```markdown
[Уровень: CRITICAL/HIGH/MEDIUM] Краткое название (где: файл/метод)
Описание: что именно происходит в коде (1-2 предложения).
Подтверждение: источник — пункт официальной документации / тест / трассировка вызовов. Уровень уверенности.
Решение: конкретные шаги фикса.
```

**STOP** — план утверждает пользователь.

### Шаг 2: Правки (по одному файлу за раз)

Правь строго один файл за раз, после каждого файла прогоняй затронутые тесты. Критические проблемы закрывай новыми юнит-тестами (mock fetch, без реальной сети — см. `umbot-write-tests`). После всех правок — полный verification-порядок: `npm run build` → `npm run test` → `npm run prettier` → `npm run lint`.

Затем документация и CHANGELOG (AGENTS.md раздел 6):

- Изменились лимиты, форматы, события или поведение адаптера → поправь `src/docs/platform-integration.md`, `src/docs/platform-contract-comparison.md` и матрицу платформ в AGENTS.md (раздел 9). Правка контракта без правки документации оставляет в доке заведомо неверные цифры.
- Запись в CHANGELOG (`Исправлено` / `Добавлено`) — в секцию по правилам AGENTS.md раздела 6: `[Unreleased]` не использовать; верхняя невыпущенная секция (без даты / с будущей датой / равная версии из `package.json`) — целевая; нет такой секции — спроси у пользователя версию и срок релиза.

Если фикс требует изменения публичного API адаптера (breaking) — STOP и вопрос пользователю.

### Шаг 3: Повторный аудит

Свежим взглядом по чек-листу: не появились ли новые несоответствия после правок (лимиты, форматы, BC публичного API). Итоговый отчёт: что закрыто, что осталось и почему.

## Что ищем

### 1. Контракты API (приоритет №1)

Цель — платформа никогда не отвечает 400 Invalid payload на легитимный сценарий:

- **Структура JSON**: вложенность массивов (Telegram `inline_keyboard` — массив массивов, не плоский), обязательные поля, null против undefined.
- **Типы**: string vs number (VK `random_id` int32, `chat_id` vs `user_id`), булевы флаги.
- **Взаимоисключающие поля**: Telegram `url` ↔ `callback_data` в одной кнопке; VK `keyboard` ↔ `template`.
- **Лимиты**: длина текста, размер payload/callback_data, кнопок в ряду, элементов галереи, размер тела запроса (Viber 30 КБ в `ViberRequest.call()`).
- **Пустые значения**: пустой `title` кнопки; `response.text` без `tts` (Алиса допускает пустой text только при заполненном tts).
- **URL**: платформа требует `https://`, а адаптер пропускает `http://` — баг контракта.

Сверяйся с матрицей платформ в AGENTS.md (раздел 9) и разделом «Verified» — там подтверждённые факты по лимитам.

### 2. Целостность адаптеров

- Кнопка-ссылка (`hide`, `url`): Telegram — `InlineKeyboardButton` с `url`, Алиса — свой формат. Как деградирует адаптер, не поддерживающий ссылки?
- `Card.getCards(cardProcessing, controller)`: у Telegram/VK/Алисы/Маруси/MAX процессоры **асинхронные** — вызов обязан быть с `await`; у Viber/SmartApp — синхронные, лишний `await` не нужен. Не копируй вызов из чужого адаптера вслепую (AGENTS.md 9.1).
- `button.options` — доступ только через `?.` / `?? {}`: кнопка может быть собрана вручную вне компонента `Buttons` (JS-потребители, тесты). Образцы: Telegram/VK/Max/Viber.
- Сериализация payload: `serializePlatformPayload` + `tryParse` из `platforms/Base/utils.ts`, не ручной `JSON.stringify`.
- `Request._getOptions()` возвращает `undefined` при ошибке attach — проверяй перед `fetch`, иначе уйдёт паразитный GET.
- Служебные события платформы → `skipAutoReply`, НЕ `setQueryData() === false` — иначе платформы включают ретраи и отключают вебхук (AGENTS.md 9.1).
- Проверка подписи: `isCorrectQuery` / `signatureName` — реальные заголовки (`x-telegram-bot-api-secret-token`, VK `secret_key` в теле, Viber `x-viber-content-signature`, MAX `x-max-bot-api-secret` — заголовок входящего вебхука; `Authorization: <token>` у MAX — auth исходящих API-запросов, не подпись вебхука). Алиса/Маруся/SmartApp подписи не шлют — их payload полностью атакующий-контролируем, включая `user_id`.

### 3. Соответствие продуктовым приоритетам (не критерий бага!)

Фреймворк универсальный: голосовые платформы (Алиса, Маруся, SmartApp) — приоритет при **добавлении новых фич**, но существующие фичи мессенджеров (inline-кнопки, markdown, опросы) — легитимная функциональность, а не «архитектурная ошибка». Помечай MEDIUM только случаи, когда фича мессенджера **не имеет безопасной деградации** на голосовой платформе (например, `request_contact` без fallback-текста в адаптере голосовой платформы).

### 4. CLI-генерируемая платформенная поверхность

`cli/` — тоже продуктовая поверхность: `flowGenerator.js` и `cli/template/` генерируют проекты, которые пользователи запускают в прод. Если аудит затрагивает форматы ответов, карточки, кнопки, HTTP-действия или токены — проверь `cli/flowGenerator.js`, `cli/template/` и `tests/cli/flowGenerator.test.ts`: те же лимиты платформ, ограниченные HTTP-таймауты и правила обработки секретов, что и в `src/plugins/`.

## Уровни критичности

- **CRITICAL** — платформа гарантированно ответит ошибкой на легитимном сценарии, либо ответ никогда не доходит до пользователя.
- **HIGH** — контракт нарушен на граничных случаях (лимиты, пустые поля), либо фича молча не работает у части пользователей.
- **MEDIUM** — несоответствие, не ломающее прод, но затрудняющее поддержку; отсутствие безопасной деградации фичи на другой парадигме (voice ↔ visual).
- **SUGGESTION** — улучшение без текущего бага.
